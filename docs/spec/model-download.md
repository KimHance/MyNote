## 기획

### 왜

받기 경로가 "원격 파일이 바뀔 때" 를 대비한 장치를 들고 있다. 받기 전에 HEAD 를 한 번 보내 허브 전용 헤더 셋으로 `.plan` 을 만들고, 헤더 하나만 빠져도 `no-plan` 으로 통째 실패한다. 그런데 받는 주소가 커밋에 고정이라 원격은 바뀌지 않는다. 서버가 보낸 대기 시간(`Retry-After`)은 읽어서 넘기지만 워커가 버린다. 재시도 'N초 뒤' 는 상태가 바뀔 때 한 번 계산되고 줄지 않는 숫자다. 알림은 진행 · 결과 · 재시도 세 갈래와 앱이 따로 올리는 Wi-Fi 대기 알림이 서로를 지우지 않아, 취소한 뒤에도 대기 · 재시도 알림이 남고 다시 시도하는 동안에도 실패 알림이 남는다.

### 누구

| 누가 | 언제 쓰나 |
|---|---|
| 퀴즈를 처음 쓰는 사람 | 노트 끝 퀴즈 CTA 나 설정의 모델 카드에서 받기를 누를 때 |
| 받는 중 앱을 나간 사람 | 알림으로 진행 · 결과를 보고, 취소하거나 다시 시도할 때 |
| 옛 판에서 받다 멈춘 사람 | 앱을 업데이트한 뒤 이어 받을 때 |
| 앱 개발자 | 모델 커밋을 올린 판을 낼 때 |

### 흐름

1. CTA `받기`(확인 다이얼로그 뒤) 또는 설정 `받기` → 알림 권한이 없으면 요청(결과와 무관) → Wi-Fi 대기 또는 준비.
2. Wi-Fi 가 있으면 곧바로 본문을 받는다. 원격에 크기 · 해시를 묻는 단계가 없다. 진행은 카드 · 알약 · 알림 하나로 보인다.
3. 받기가 끊기면(연결이 끊김 · 서버 오류) 쉬었다가 받은 자리부터 이어 받는다. 언제 · 무엇이 되면 다시 받는지는 약속하지 않고, 남은 시간도 어디에도 보이지 않는다.
4. 다 받으면 파일 확인 → 사용 가능. 알림은 결과(받았습니다) 하나만 남는다.
5. 취소하면 멈춤(받은 만큼 남음)이고 알림은 하나도 남지 않는다. 실패하면 결과(받지 못했습니다) 하나에 `다시 시도`.

### 동작

확인 칸: `JVM` = MockWebServer · 순수 함수 단위 시험(시험 이름에 항목 ID). `리뷰 grep` = 검수가 저장소를 grep 해 센다. `수동(가짜 상태)` = 기기의 모델 파일과 받기 작업을 건드리지 않고 본다 — 카드 · 알약은 `@Preview`(PreviewParameter 로 상태별)를 사람이 IDE 에서 보고, 알림은 JVM 순수 함수 시험이 판단의 원본이며, 실물 모양은 **메인이 run 끝에 한 번** 기기에서 본다(결정 10). 워커는 기기에서 받기 작업을 돌리지 않는다. `수동(기기 · 메인)` = 2026-10-07 메인이 에뮬레이터에서 모델 파일을 이름만 옮겨 두고 받기 작업을 돌려 본 것(결정 10) — 본 것 / 못 본 것을 칸에 적는다. `수동(읽기)` · `수동(코드 대조)` = 파일 · 원격 · 코드를 읽기만 한다.

| MD-2 | 끝 검증의 기준은 앱에 박힌 크기와 sha256 이다. 둘 다 맞아야 자리에 들어간다. 안 맞으면 조각을 버리고 처음부터 받고, 8라운드 안에 못 맞추면 `too-many-rounds` 로 실패한다. 이미 자리에 있는 파일도 같은 기준으로 본다 | 기대 크기 · 해시와 같은 본문 → 설치(자리 파일 = 본문, 조각 없음). 크기는 같고 내용이 다른 본문 → 자리에 들어가지 않고 조각을 버린 뒤 처음부터 다시 요청한다. 늘 다른 내용을 주는 서버 → 본문 요청 8회 이하로 `too-many-rounds`. 앱에 박힌 해시 · 크기가 결정 7 의 값이다(소문자 hex 64자 · 2,588,147,712) | JVM: `MD-2 기대 크기와 해시가 맞으면 자리에 들어간다` · `MD-2 해시가 다르면 버리고 처음부터 받는다` · `MD-2 끝내 안 맞으면 8라운드에서 멈춘다` · `MD-2 앱 상수는 소문자 hex 64자 sha256 과 2588147712 바이트다` · 수동(읽기): 두 출처 대조는 메인이 마쳤다(결정 7) · 수동(기기 · 메인): 이름을 되돌린 에뮬레이터 설치본이 2588147712 바이트 · sha256 = 결정 7 값 |
