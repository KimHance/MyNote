## 기획

### 왜

받기 경로가 "원격 파일이 바뀔 때" 를 대비한 장치를 들고 있다. 받기 전에 HEAD 를 한 번 보내 허브 전용 헤더 셋으로 `.plan` 을 만들고, 헤더 하나만 빠져도 `no-plan` 으로 통째 실패한다. 그런데 받는 주소가 커밋에 고정이라 원격은 바뀌지 않는다. 서버가 보낸 대기 시간(`Retry-After`)은 읽어서 넘기지만 워커가 버린다. 재시도 'N초 뒤' 는 상태가 바뀔 때 한 번 계산되고 줄지 않는 숫자다. 알림은 진행 · 결과 · 재시도 세 갈래와 앱이 따로 올리는 Wi-Fi 대기 알림이 서로를 지우지 않아, 취소한 뒤에도 대기 · 재시도 알림이 남고 다시 시도하는 동안에도 실패 알림이 남는다.

### 누구

| 누가 | 언제 쓰나 |
|---|---|
| 퀴즈를 처음 쓰는 사람 | 노트 끝 퀴즈 CTA 나 설정의 모델 카드에서 받기를 누를 때 |
| 받는 중 앱을 나간 사람 | 알림으로 진행 · 결과를 보고, 취소하거나 다시 시도할 때 |
| 옛 판에서 받다 멈춘 사람 | 앱을 업데이트한 뒤 이어 받을 때 |
| 앱 개발자 | 모델 커밋을 올린 판을 낼 때 |

### 흐름

1. CTA `받기`(확인 다이얼로그 뒤) 또는 설정 `받기` → 알림 권한이 없으면 요청(결과와 무관) → Wi-Fi 대기 또는 준비.
2. Wi-Fi 가 있으면 곧바로 본문을 받는다. 원격에 크기 · 해시를 묻는 단계가 없다. 진행은 카드 · 알약 · 알림 하나로 보인다.
3. 받기가 끊기면(연결이 끊김 · 서버 오류) 쉬었다가 받은 자리부터 이어 받는다. 언제 · 무엇이 되면 다시 받는지는 약속하지 않고, 남은 시간도 어디에도 보이지 않는다.
4. 다 받으면 파일 확인 → 사용 가능. 알림은 결과(받았습니다) 하나만 남는다.
5. 취소하면 멈춤(받은 만큼 남음)이고 알림은 하나도 남지 않는다. 실패하면 결과(받지 못했습니다) 하나에 `다시 시도`.

## 명세

### 동작

확인 칸: `JVM` = MockWebServer · 순수 함수 단위 시험(시험 이름에 항목 ID). `리뷰 grep` = 검수가 저장소를 grep 해 센다. `수동(가짜 상태)` = 기기의 모델 파일과 받기 작업을 건드리지 않고 본다 — 카드 · 알약은 `@Preview`(PreviewParameter 로 상태별)를 사람이 IDE 에서 보고, 알림은 JVM 순수 함수 시험이 판단의 원본이며, 실물 모양은 **메인이 run 끝에 한 번** 기기에서 본다(결정 10). 워커는 기기에서 받기 작업을 돌리지 않는다. `수동(읽기)` · `수동(코드 대조)` = 파일 · 원격 · 코드를 읽기만 한다.

| ID | 동작 | 받아들임 기준 | 확인 |
|---|---|---|---|
| MD-1 | 받기는 원격에 크기 · 해시를 묻지 않고 곧바로 본문을 요청한다. 허브 전용 헤더(`x-linked-size` · `x-linked-etag` · `x-repo-commit`)에 기대지 않는다 | MockWebServer 에서 설치 한 번 동안 기록된 요청이 모두 GET 이고 HEAD 는 0개다. 응답에 세 헤더가 하나도 없어도 설치가 끝난다 | JVM: `MD-1 받기는 HEAD 없이 본문 요청부터 한다` · `MD-1 허브 헤더가 없어도 받는다` |
| MD-2 | 끝 검증의 기준은 앱에 박힌 크기와 sha256 이다. 둘 다 맞아야 자리에 들어간다. 안 맞으면 조각을 버리고 처음부터 받고, 8라운드 안에 못 맞추면 `too-many-rounds` 로 실패한다. 이미 자리에 있는 파일도 같은 기준으로 본다 | 기대 크기 · 해시와 같은 본문 → 설치(자리 파일 = 본문, 조각 없음). 크기는 같고 내용이 다른 본문 → 자리에 들어가지 않고 조각을 버린 뒤 처음부터 다시 요청한다. 늘 다른 내용을 주는 서버 → 본문 요청 8회 이하로 `too-many-rounds`. 앱에 박힌 해시 · 크기가 결정 7 의 값이다(소문자 hex 64자 · 2,588,147,712) | JVM: `MD-2 기대 크기와 해시가 맞으면 자리에 들어간다` · `MD-2 해시가 다르면 버리고 처음부터 받는다` · `MD-2 끝내 안 맞으면 8라운드에서 멈춘다` · `MD-2 앱 상수는 소문자 hex 64자 sha256 과 2588147712 바이트다` · 수동(읽기): 두 출처 대조는 메인이 마쳤다(결정 7) |
| MD-3 | 용량 확인은 첫 요청 전에 앱에 박힌 크기로 한다. 받아 둔 조각만큼은 빼고 센다. 모자라면 요청 없이 `no-space` 로 실패한다 | 쓸 수 있는 공간 < 크기 − 조각 → 서버 요청 0회 · `no-space`. 조각 10바이트가 있으면 크기 − 10 만큼만 요구한다 | JVM: `MD-3 공간이 모자라면 한 번도 요청하지 않는다` · `MD-3 받아 둔 조각만큼은 덜 요구한다` |
| MD-4 | 옛 판(원격에 묻던 판)에서 받다 멈춘 기기: 남은 조각은 그 자리부터 이어 받는다. 옛 판이 남긴 `.plan` 은 읽지 않고, 설치나 받던 파일 지우기 뒤에 남지 않는다. 상태의 전체 크기는 진행률 → 앱에 박힌 크기 순이다 | 조각 10바이트 + `.plan`(다른 커밋 · 깨진 JSON 둘 다) → 첫 본문 요청이 `Range: bytes=10-` 이고 설치가 끝나며 `.plan` 이 없다. 조각 + `.plan` 에서 받던 파일 지우기 → 둘 다 없다. 진행률에 전체 크기가 없으면 상태의 전체는 앱에 박힌 크기다(`.plan` 값과 무관) | JVM: `MD-4 옛 plan 이 있어도 조각을 이어 받고 plan 을 남기지 않는다` · `MD-4 받던 파일 지우기는 옛 plan 도 지운다` · `MD-4 전체 크기는 plan 을 보지 않는다` |
| MD-5 | 모델 커밋을 바꾼 판에서 옛 커밋 조각이 남아 있어도 섞인 파일은 자리에 들어가지 않는다 — 끝 검증(MD-2)이 막고 처음부터 다시 받는다 | 다른 내용의 조각 5바이트가 있으면 이어 받은 뒤 해시가 안 맞아 버리고, 처음부터 받아 자리 파일이 기대 본문과 같다(본문 요청 2회) | JVM: `MD-5 다른 파일의 조각은 섞이지 않고 처음부터 다시 받는다` |
| MD-6 | 실패 이유는 `no-space` · `no-progress` · `too-many-rounds` · `HTTP n` · `unknown` 이다. `no-plan` 은 없어진다. 옛 판이 `no-plan` 으로 남긴 실패 기록은 일반 실패로 보이고 `다시 시도` 로 받는다 | 실패 이유 상수에 `no-plan` 이 없다. `Failed("no-plan")` 의 카드 세부 · 도움말 · 실패 알림 본문이 일반 실패(공간 부족 아님)이고 버튼은 `다시 시도` 다 | JVM: `MD-6 옛 no-plan 실패는 일반 실패 카드로 보인다` · `MD-6 옛 no-plan 실패 알림은 기본 문구다` |
| MD-7 | 408 · 429 · 5xx · 연결 오류는 재시도로 넘어간다. 서버가 보낸 대기 시간(`Retry-After`)은 읽지 않는다. 재시도 간격은 작업 예약의 지수 백오프(30초부터)다 | `429 + Retry-After: 120` 과 헤더 없는 `429` 가 같은 결과(재시도)다. 재시도 결과에 대기 시간 칸이 없다. 404 · 403 은 지금처럼 `HTTP n` 실패다 | JVM: `MD-7 429 는 Retry-After 와 무관하게 재시도한다` |
| MD-8 | 재시도 상태는 남은 시간을 갖지 않는다 — 받은 만큼과 전체만 안다. 카드 · 알약 · 알림 어디에도 초가 없다. 재시도 중에 보이는 것은 ① 받기가 끊겼다 ② 받은 자리부터 이어 받는다 ③ 받은 만큼(멈춘 막대) ④ `취소` 다. ② 는 **시점 · 계기를 약속하지 않는 말**이다('곧' · '연결되면' 이 아니다) — 재시도에는 Wi-Fi 가 붙은 채 서버 오류(408 · 429 · 5xx) 뒤 백오프로 기다리는 때도 들어 있다(결정 13). 글자는 디자인 문서 | 대기 중 + 한 번 이상 돈 작업 + 조각 1GB → `Retrying(1GB, 전체)` 이고 판정이 예정 시각 · 지금 시각을 받지 않는다. 카드: 재시도 라벨 · 세부는 인자 없는 고정 문구 · warn 막대 = 받은 비율 · 버튼 `취소`. 알약: 보조 글자에 초가 없다. 문자열에 초 자리가 남지 않는다 | JVM: `MD-8 재시도 상태는 남은 시간 없이 받은 만큼만 안다` · `MD-8 재시도 카드는 초 없이 이어 받는다고 말한다` · `MD-8 재시도 알약에는 초가 없다` · 리뷰 grep: `notes_pill_seconds` 0건 · `notes_model_retrying_desc` 값에 `%` 0건 · 수동(가짜 상태): 카드 · 알약 `@Preview`(재시도 포함 상태별) — 실물은 메인 끝 1회(결정 10) |
| MD-9 | 떠 있는 내려받기 알림은 상태로 정해지고 한 번에 하나다(아래 알림 표). "하나" 는 알림 자리가 하나라는 뜻이 아니라, 하나를 올리면 다른 자리를 지워 한 번에 떠 있는 것이 하나라는 뜻이다. 결과 알림과 진행 계열 알림이 함께 떠 있지 않다. 재시도 알림은 시점 · 계기를 약속하지 않고(결정 13) 작은 아이콘이 움직이지 않는다(결정 12) | 상태 → 알림 매핑이 알림 표와 같다(9상태 전부). 재시도 알림 본문에 `곧` · 초 · `연결되면` 같은 시점 · 계기 약속이 없고, 막대가 받은 비율에서 멈춰 있고, 작은 아이콘이 움직이지 않는 쪽이다. 파일 확인 알림에만 `취소` 가 없다 | JVM: `MD-9 상태마다 알림이 하나로 정해진다` · 리뷰 grep: core/ai 의 재시도 알림 본문 문자열 값에 `곧` · `초` · `연결되면` 0건 · 수동(가짜 상태): 판단은 JVM 표 시험이 원본 · 실물 모양은 메인 끝 1회 기기(결정 10) |
| MD-10 | 상태가 바뀔 때 알림이 남지 않는다. ① 새 받기 시작(대기 · 준비) → 남은 결과 알림이 사라진다 ② 취소(앱 · 알림 액션 어디서든, 작업이 돌던 중이든 대기 · 재시도로 쉬던 중이든) → 진행 계열 알림이 모두 사라지고 결과 알림을 띄우지 않는다 ③ 성공 → 진행 계열이 사라지고 결과(받았습니다) 하나 ④ 실패 → 결과(받지 못했습니다) 하나 ⑤ 모델 삭제 → 남은 결과 알림이 사라진다 | 가짜 알림판으로 이 순서를 돌려 남은 알림을 센다: 실패 알림이 있는 채 다시 시도 → 실패 알림 0 · Wi-Fi 대기 중 취소 → 0 · 재시도 중 취소 → 0 · 재시도 → 성공 → `받았습니다` 1 · `받았습니다` 가 있는 채 모델 삭제 → 0 | JVM: `MD-10 다시 시도하면 실패 알림이 사라진다` · `MD-10 쉬는 중 취소해도 알림이 남지 않는다` · `MD-10 재시도 뒤 성공하면 받았습니다 하나만 남는다` · `MD-10 모델을 지우면 결과 알림도 사라진다` |
| MD-11 | 쉬는 동안(Wi-Fi 대기 · 재시도)의 알림이 뜨는 때: ① 앱이 뒤로 갈 때 상태가 Wi-Fi 대기면 대기 알림, 재시도면 재시도 알림 ② 연결 오류로 재시도가 예약되면 재시도 알림 ③ 받는 중 작업이 사용자 취소가 아닌 이유(Wi-Fi 끊김 · 시스템)로 멈추면 재시도 알림이 남는다(지금은 아무것도 안 남는다) | 멈춘 이유 → 남길 알림: 사용자 취소 → 없음, 그 밖 → 재시도 알림. 앱이 뒤로 갈 때: Wi-Fi 대기 → 대기 알림 · 재시도 → 재시도 알림 · 그 밖 → 알림을 건드리지 않는다 | JVM: `MD-11 사용자가 멈춘 게 아니면 재시도 알림을 남긴다` · `MD-11 앱이 뒤로 가면 쉬는 상태의 알림을 올린다` |
| MD-12 | 알림 권한이 없어도(13+ 거부 · 앱 알림 끔) 받기는 그대로 돈다 — 알림만 안 보인다. 설정 카드의 알림 꺼짐 안내 + `켜기` 는 작업 중 5상태(Wi-Fi 대기 · 준비 · 받는 중 · 재시도 · 파일 확인)에서만 보인다. 띄우는 상태는 이 문서가 정하고 디자인은 안내 문구만 본다(결정 14) | 카드 매핑이 안내를 보일지를 상태로 정한다 — 작업 중 5상태만 참이고 멈춤 · 없음 · 사용 가능 · 실패는 거짓이다 | JVM: `MD-12 알림 꺼짐 안내는 작업 중에만 보인다` · 수동(가짜 상태): 카드 `@Preview`(알림 꺼짐 × 상태별) — 실물은 메인 끝 1회(결정 10) |
