# write-note

노트 앱은 **GitHub 저장소의 `notes/` 를 읽어서** 그립니다. 그래서 노트를 저장·수정·삭제한다는 것은 노트 파일을 저장소에 커밋하고 push 하는 일입니다. 이 스킬은 그 일을 규격에 맞게, 안전하게 합니다.

## 역할 나눔

- 이 스킬은 **대화 내용을 마크다운 노트로 쓰는 일**과 **노트 파일 하나를 커밋하는 일**만 합니다.
- `notes/index.json` 과 해시는 **만들지도 고치지도 않습니다.** 저장소의 Action 이 push 를 보고 대신 만듭니다.

## 규격

규격은 플러그인에 든 `${CLAUDE_PLUGIN_ROOT}/SPEC.md` 에 있습니다. **노트를 쓰기 전에 이 파일을 읽고 그대로 따릅니다.** 이 스킬에는 규격을 옮겨 적지 않았습니다. 옮겨 적으면 규격이 바뀔 때 어긋나기 때문입니다.

- 쓰는 곳은 `notes/<그룹>/<id>.md` 입니다. 그룹은 폴더 이름, `id` 는 파일 이름이고 저장소 전체에서 유일해야 합니다.
- 파일 맨 위에 앞머리를 두고 `title` · `date` 두 키만 적습니다. 그 아래가 마크다운 본문입니다. 앞머리 문법과 쓰기 규칙은 규격의 앞머리 · 쓰기 규칙 절을 따릅니다.
- 규격이 **글자로만 보인다**고 한 문법(링크 · 이미지 · HTML · 수식 · 형광 · 각주 · 알림)은 쓰지 않습니다. 앱이 블록으로 그리는 문법만 씁니다.
- 노트 제목은 앞머리에 있으니 본문 첫 줄에 `#` 제목으로 되풀이하지 않습니다.
- 이미 있는 노트를 하나 읽어 보면 모양과 문체를 가장 빨리 알 수 있습니다.

## 지킬 것

1. **작업 전에 `git pull --rebase` 를 합니다.** 저장 · 수정 · 삭제 모두 같습니다.
2. **노트 파일만 스테이징하고 커밋합니다.** 다른 변경을 섞지 않습니다. `index.json` 은 스테이징하지 않습니다.
3. 커밋은 사용자의 git 신원으로 합니다. `git` 만 씁니다. 커밋 훅을 건너뛰는 옵션은 권하지도 쓰지도 않습니다.
4. **미리보기를 보여 주고 확인을 받은 뒤에 씁니다.** 제목 · 날짜 · 그룹 · `id` · 본문 요약을 보여 줍니다.
5. **push 가 성공해야 끝입니다.** 앱은 로컬 클론이 아니라 GitHub 를 읽으므로 push 되지 않은 커밋은 앱에서 보이지 않습니다. push 뒤에 올라갔는지(`git status` 가 브랜치가 앞서 있지 않다고 말하는지) 확인하고 나서야 저장됐다고 말합니다. push 가 안 됐으면 안 됐다고 그대로 말합니다.
6. **저장소가 템플릿에서 왔는지 봅니다.** `.github/workflows/` 에 노트 index 를 만드는 workflow 가 없으면 "index 를 만들어 줄 Action 이 없어서 앱에 새 노트가 안 보일 수 있습니다" 라고 알립니다. 이때도 `index.json` 을 직접 만들지는 않고, 검사 도구의 `index` 명령을 안내만 합니다.

## 작업별 순서

### 저장

1. `git pull --rebase`
2. `${CLAUDE_PLUGIN_ROOT}/SPEC.md` 를 읽고 `id` 가 이미 쓰이지 않는지 `notes/` 에서 확인합니다(`.md` 와 옛 `.json` 둘 다).
3. 대화 내용을 마크다운 본문으로 씁니다. 작은 생각은 작게, 큰 주제는 `##` 절로 나눕니다.
4. 미리보기를 보이고 확인을 받습니다.
5. `notes/<그룹>/<id>.md` 를 씁니다. 앞머리 `date` 는 오늘 날짜(`YYYY.MM.DD`)입니다.
6. 쓴 파일이 규격에 맞는지 `check-notes` 스킬로(또는 `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/note_tool.py" check`) 확인합니다.
7. `git add notes/<그룹>/<id>.md` → `git commit -m "notes: add <제목>"` → `git push` → 올라갔는지 확인

### 수정

1. `git pull --rebase`
2. 대상 노트를 읽고 요청한 부분만 고칩니다.
3. 대상이 옛 `.json` 노트면 **같은 `id` 의 `.md` 로 옮깁니다.** 미리보기에 "형식을 마크다운으로 바꿉니다" 를 함께 보여 줍니다. 제목 · 날짜는 앞머리로, 블록은 같은 뜻의 마크다운으로 옮깁니다.
4. 미리보기 → 확인 → 같은 파일만 `git add` (옮긴 경우는 새 `.md` 를 `git add` 하고 옛 `.json` 은 `git rm` 으로 지웁니다 — 둘이 같은 커밋에 들어가야 합니다. 같은 `id` 가 두 파일에 있으면 검사가 실패합니다) → `git commit -m "notes: update <제목>"` → `git push` → 확인

### 삭제

1. `git pull --rebase`
2. 대상을 확인하고 지우기 전에 무엇이 사라지는지 보여 준 뒤 확인을 받습니다.
3. `git rm notes/<그룹>/<id>.md`(옛 노트면 그 `.json`) → `git commit -m "notes: remove <제목>"` → `git push` → 확인

## 실패했을 때

- push 가 거절되면 `git pull --rebase` 를 하고 다시 push 합니다.
- 규격 검사가 실패하면 파일 경로와 이유를 그대로 전하고, 노트를 고친 뒤 다시 확인합니다. 마크다운 노트는 대개 앞머리가 틀린 것입니다.
- 저장소의 Action 이 push 뒤에 `index.json` 을 커밋하므로, 다음 작업 전에 `git pull --rebase` 를 하면 그 커밋이 들어옵니다.

## 예시

**요청:** "방금 얘기한 코루틴 디스패처 내용을 노트로 저장해줘"

**흐름:** `git pull --rebase` → `${CLAUDE_PLUGIN_ROOT}/SPEC.md` 확인 → 그룹 `kotlin`, `id` `coroutine-dispatchers` 로 구성 → 미리보기 · 확인 → 아래 파일 하나(`notes/kotlin/coroutine-dispatchers.md`)를 커밋 → push 하고 올라갔는지 확인

```markdown
---
title: 코루틴 디스패처 고르기
date: 2026.01.01
---
## 어떤 디스패처를 언제

디스패처는 코루틴이 **어느 스레드에서 도는지** 를 정합니다.

- `Dispatchers.Default` — CPU 작업
- `Dispatchers.IO` — 블로킹 I/O

> 작업 성격에 맞춰 고릅니다.
```
